## 2. 主要发现：扫描周期和超期结论是观测假象

### 2.1 机制

`ScanMonitor`（`e2e/client.py:53-92`）是客户端进程里的一个线程，和主线程共用 GIL：

- 主线程在 `client.py:191` 忙等（`while clock() < target: pass`），只有到了 CPython 的强制切换间隔（`sys.getswitchinterval()`，5 ms）才让出 GIL。而监视器每次从 `time.sleep(0.0005)`（第 92 行）或 socket I/O 返回，都要重新拿到 GIL 才能继续；
- ack 轮询（`client.py:248-254`）在紧循环里反复获取 `modbus_lock`。Python 的锁不保证公平，监视器还会卡在第 75 行。

结果是监视器看到心跳变化的时刻，比真实 tick 晚 0 到 10 ms 以上。相邻两次观测之差等于 10 ms + lag(n) − lag(n−1)，于是出现"拉长到约 21 ms、随后约 0.6 ms 追赶、均值不变"的形态。滞后超过一个周期时，心跳一次跳 2，被记为"观测间隙"。

空闲时主线程不忙等，监视器不受影响，所以空闲基线是 10.00 ms、0% 迟到。**空闲基线分不开"PLC 在负载下变慢"和"观测者在负载下被饿住"这两种情况。** 这个机制出在解释器层面（CPython 3.10，5 ms 切换间隔），板上和开发机上一样。

### 2.2 复现

`review_tools/fakeplc.py` 的心跳值是 floor((now − t0) / 10 ms)，没有调度、抖动或超期。写入的命令在下一个扫描边界被 ack，和冻结的 ST 程序一致。

`observer_check.sh` 让 `841914f` 的 `client.py`、`wrapper.py` 原样对它运行空闲、bypass、instrumented 三种模式，冻结 PEP 照常在环，每种模式 3,000 条命令。同时，独立进程的 `reference_observer.py` 在同一负载下观测。pymodbus 替身每次调用的开销比真实 pymodbus 小，所以测出的饥饿只会偏轻。

| | 硬件组 v3（Jetson，真实 OpenPLC） | 假 PLC，被审的进程内监视器 | 假 PLC，独立进程参考观测者 |
|---|---|---|---|
| 空闲：迟到 tick（>12 ms） | 0.0% | 0.05% | 0.15% |
| bypass：迟到 tick | 20.1–20.3% | 23.6% | 0.37% |
| instrumented：迟到 tick | 27.3–27.5% | 29.5% | 0.23% |
| instrumented − bypass（"ZoneCap 边际"） | +7.3 pp | +5.9 pp | −0.1 pp |
| 观测间隙 | 2.1–2.9% | 1.8–2.1% | — |
| 观测周期 p99 / 最小 / 均值 | ≈21 / 0.8 / 10.05–10.13 ms | 20.8–21.0 / 0.6 / 10.04–10.09 ms | — |
| 观测滞后 p50 / p99 | — | — | 0.33 / 0.63–0.66 ms |

结果可以重复：当天另外三次 bypass 运行（其中一次换了种子）的迟到比例是 21.8–22.5%，另外两次 instrumented 运行都是 29.2%。参考观测者偶有 6–9 ms 的离群滞后，空闲时也出现，来源是共享开发机的背景负载。

一个零抖动的 PLC，被同一方法测出了同样的迟到比例和同样的模式差。所以 §3.2 的两条解读都没有证据支持：一是"Python modbus_slave 插件与调度器同核竞争，引入拉伸和追赶"；二是"ZoneCap 在环边际 = 迟到比例 +7.3 pp"。这并不证明真实 OpenPLC 在负载下没有延迟，只说明现在的方法分辨不出来。

### 2.3 相位戳

假 PLC 的真实 tick 时刻已知，所以每条命令的真实相位就是 (t_send − t0) mod 10 ms，可以直接和记录的 `phase_us`（`client.py:193`）对比。循环误差最大为 5 ms：

| | 误差 p50 | p90 | p99 |
|---|---|---|---|
| bypass | 2.15 ms | 4.44 ms | 4.93 ms |
| instrumented | 2.56 ms | 4.57 ms | 4.94 ms |
| 完全随机猜（参照） | 2.5 ms | 4.5 ms | 4.95 ms |

记录的相位和随机猜没有区别。§6 要求"把扫描相位等待（0–10 ms）和处理时间分开"，现在做不到；§3.2 中"扫描相位等待 0–10 ms 可分离"的说法应撤回。

不受影响的部分：
- 真实到达相位是均匀的：3,000 条命令落进 10 个 1 ms 区间，每格 263–334 条。所以 §6 对到达过程的要求是满足的。
- 发送到 ack 的总时延和 decide 段，由主线程和 wrapper 自己计时，基本可信（ack 的观测可能晚一次读往返）。v3 的 total 和 decide 分位数不受这个问题影响。

### 2.4 超期的数据来源

`run_e2e.py:186-188` 要等每个种子的两种模式都跑完，才取一次 runtime 日志，而且截成最后 20,000 个字符（第 50 行）。一个种子的两种模式合计 40 分钟以上，按执行计划所说每 5 秒一条统计，就有约 500 条，20,000 字符很可能只剩 bypass 的后段。日志里也没有模式的起止标记，两种模式根本分不开。

也就是说，唯一不依赖 Modbus 观测的超期来源，并没有覆盖 instrumented 模式。

### 2.5 再跑 e2e 开发运行之前要改的

1. **把心跳观测移到独立进程。** 放在空闲核上（e2e 里核 5 没有用到），用自己的 Modbus 连接，不和任何忙等共享解释器。两种模式和空闲基线都要运行它，并保持同样的轮询负载。原始的 `(t_ns, heartbeat)` 序列按（种子，模式）写盘。`review_tools/reference_observer.py` 可以直接用，也可以作为参照自己实现。
2. **先校准。** 新观测者在完整客户端负载下测 `fakeplc.py`，迟到 tick 应接近 0%，滞后 p99 应在 1 ms 以内（见 `review_tools/README.md`）。校准输出要放进运行目录。
3. **超期以 OpenPLC runtime 自身的统计为准。** 记录每种模式的起止时间，按窗口完整抓取（运行中定期抓，或事后按时间切片），不要截断。心跳观测只用来交叉验证。
4. **相位在事后计算。** 用独立观测者记录的边界序列给每条命令算相位：每个 tick 取最早的那次观测，或者对 t_obs − n·10 ms 取下包络。也可以把 ack 轮询改成一次读 %QW2–%QW4，同时拿到 ack 和心跳，从而知道命令是在第几次扫描被应用的。
5. **提交分析脚本。** 生成 §3.2 数字的脚本必须进仓库，否则这些数字无法复算。输出至少包括：
   - 每段时延的 nearest-rank 分位数；
   - `build_c5_results.py --e2e` 需要的 `total_p50_us`、`total_p99_us`、`overruns_with_pep`、`overruns_bypass`。

   `scan_stats.json` 也有两处要改：p50/p99 不是按 nearest-rank 算的；直方图只覆盖 8–20 ms，0.6 ms 和 20 ms 以上的观测都落在范围之外。

## 3. 仍未处理（第一轮已提出）

### 3.1 口令（最紧急）

`run_e2e.py:48` 把 OpenPLC runtime API 的账号和口令明文写在代码里。仓库是公开的，git 历史里也留着，所以只改代码不够：

- 在板上更换这个口令；
- 新口令改为从环境变量或仓库外的文件读取；
- 确认 8443 端口只在 127.0.0.1 或直连网口上监听，不对 WiFi 开放。

### 3.2 溯源

- 运行目录不记录 git commit 和工作区是否干净；确认性运行也不拒绝脏工作区。
- `command.txt`（第 204–206 行）是拼出来的，不包含实际传入的 `--python/--seeds/--warmup/--measured`。
- e2e 虚拟环境没有记录 `pip freeze`，pymodbus 版本（3.16.x）也没有锁定。
- `.so` 是用 `libplc_*.so | head -2` 取的，应改成 runtime 进程实际映射的那个（从 `/proc/<pid>/maps` 取）。
- e2e 不校验冻结源码的哈希。

### 3.3 绑核与预检

- tegrastats（`run_e2e.py:127-129`）没有绑核，可能落到核 3 上，违反 §4.4。
- `harness.pin()` 返回的 `verified`，在 `client.py:128` 和 `wrapper.py:182` 都没有检查。
- §4.5 要求观测不到 10 ms 任务周期就中止运行。目前 30 秒空闲基线不在代码里，应该做成每次运行开始时的自动预检（用 §2.5 的独立观测者），不达标就中止并保留目录。

### 3.4 流程

- 每个种子都是先 instrumented 后 bypass，建议按种子轮换顺序。
- instrumented 开始前没有复位 PLC 的命令序号。v3 零 ack 超时，暂时没有造成问题。
- `random.Random((seed, cmd_id))`（`client.py:189`）用元组做种子，CPython 3.11 起会报错。
